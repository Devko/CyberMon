# Advanced cybersecurity visualization candidates

The strongest next instruments would reuse CyberMon's real datasets while exposing relationships, histories, or counterfactuals that its existing aggregate charts cannot show. Treat these as interactive research tools: every point/edge needs a meaning, every selection needs a receipt, and every time control must distinguish event time from observation time.

These are proposed designs, not claims that the required data has already been acquired. “Reuse” means the repository already contains relevant source data or pipeline work; a new per-record export may still be required. Existing modules should gain these instruments rather than being duplicated merely to add another chart.

## Best first candidates

| Priority | Instrument | What the user sees and does | Data and additional work | Main analytical safeguard |
|---|---|---|---|---|
| 1 | **The Mutation Observatory** | Each CVE follows a dated trail through severity changes, EPSS threshold crossings, KEV entry, and enrichment. Scrub a day, isolate a burst, compare before/after, and export affected IDs. | Reuse rescore log, KEV changelog, EPSS volatility; export event-level joins and persist EPSS history beyond the current rolling map. | Show observation dates as observation dates; do not invent history before monitoring began. |
| 2 | **The Adversary Atlas** | A navigable group → software → technique network. Select a group to reveal shared tools and techniques; compare two groups and trace every edge back to its source. | Reuse MITRE ATT&CK STIX acquisition; export relationships and citations instead of just aggregate counts. | Shared tooling is not proof of shared identity or coordination. Limit the default graph to a selected neighborhood. |
| 3 | **The Exploitation Clock** | Linked event tracks from publication to dated PoC to KEV, with a marker for each event rather than one exclusive lane per CVE. Brush a cohort and compare its delay distribution. | Reuse publication/PoC/KEV joins; add date precision and source provenance to a compact event export. | PoC availability is not observed exploitation; KEV inclusion is not first exploitation. Censor unresolved events. |
| 4 | **The Enrichment Factory** | A flow diagram of CVEs moving through NVD states, with queue age and CNA/CISA contributions. Select an incoming cohort to watch what exits and what remains. | Reuse NVD state/throughput and ADP metrics; retain per-CVE transitions for true trajectories. | Current status alone cannot reconstruct past paths; distinguish unavailable history from zero transitions. |
| 5 | **The Weakness Landscape** | A zoomable CWE hierarchy with CVEs as leaves and overlays for KEV, severity, vendor, and year. Compare volume with exploitation share and follow parent/child classes. | Reuse CWE extraction and KEV join; add official CWE hierarchy and support multiple CWE tags per record. | CVE counts reflect reporting and taxonomy choices, not exposure-adjusted risk. Show untagged records. |
| 6 | **The Supply-Chain Constellation** | A package/version dependency graph with vulnerable ranges, fixed versions, and affected dependents. Change a version to compare the reachable dependency set before and after. | New OSV ingest plus dependency manifests/SBOMs or a dependency graph source. | A vulnerable dependency in a graph is not necessarily reachable in application execution; state that limitation. |

For the next release I would choose **Mutation Observatory**: it makes CyberMon's accumulating history useful in a way a static dashboard cannot. **Adversary Atlas** offers the strongest visual contrast with the Field. **Supply-Chain Constellation** has high practical value but the largest additional data burden of these six.

MITRE publishes STIX objects and relationships suitable for the Adversary Atlas: [ATT&CK data and tools](https://attack.mitre.org/resources/attack-data-and-tools/). OSV supports querying vulnerabilities and downloading ecosystem data, but it does not by itself supply a complete dependency graph: [OSV API](https://google.github.io/osv.dev/api/), [OSV data sources](https://google.github.io/osv.dev/data/).

For patch-priority work, FIRST explicitly warns against multiplying ordinal CVSS by EPSS and explains coverage/effort evaluation: [Using EPSS](https://www.first.org/epss/using-epss). For a grounded post-quantum demonstration, OQS publishes performance visualizations: [OQS benchmarking](https://openquantumsafe.org/benchmarking/).

## Shared instrument requirements

Build the next instrument on a small shared layer rather than copying the entire Field script:

- **Stable identity and provenance:** canonical record/event IDs, source links, generation time, observation time, and an explicit edition.
- **One visibility model:** filters, time, group limits, canvas, table, counters, and export must agree on the same set.
- **Progressive detail:** useful overview, collision-managed labels, local neighborhoods, then individual records. Avoid an unreadable all-nodes graph.
- **Receipts:** every selection exposes members, definitions, denominators, and downloadable data.
- **Comparable views:** a 2D analytical view and an accessible table alongside spatial exploration.
- **Honest time:** distinguish event time, first observation, publication, and current snapshot. Render unknown history explicitly.
- **Reproducible sharing:** serialize filters, layout, relevant camera/selection, and edition or clearly state that a link follows the latest edition.
- **Measured performance:** render on demand, use GPU picking with verified hit areas, budget labels, and benchmark representative mobile hardware.

The point is to help users answer a question that the existing charts cannot answer: which exact records changed, which entities share evidence, which sequence occurred, or what a stated intervention changes. A new arrangement alone is usually an enhancement to an existing instrument.
